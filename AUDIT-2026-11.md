# Audit, November 2026: can lossless convexification work for our vehicle?

Question asked: is there a mistake in this repository that, once fixed, would let us use lossless convexification
(LCvx) on the 6-DoF lander? If not, what should we fly? This file answers the first part and records what was
checked. The second part is the landing algorithm (planner F): [LANDING-ALGORITHM.md](LANDING-ALGORITHM.md), its proof
[math/10-landing-proof.md](math/10-landing-proof.md) and its benchmarks [solver/RESULTS-FLAT.md](solver/RESULTS-FLAT.md).

## Verdict

**No. The impossibility result stands.** No convex program that takes the initial position and velocity the way LCvx
does can be exact for our vehicle. I found no error in the proof chain, and I reproduced the obstruction
independently on the planner's own vehicle model.

**But one practical conclusion drawn from it was wrong.** The repository concluded that "every practical method
must iterate on the attitude". The theorem does not say that, and it is false. A single convex program can be
*sound* (every plan it returns is flyable) as long as it is not also *complete* (it may refuse or over-charge some
flyable landings). The repository already contained the tool that makes such a program work for a gimballed vehicle,
the centre-of-percussion identity, but used it only in the tracking controller. Planner F uses it for planning.

**The quoted result ("6-DoF powered descent as a single convex program") is not a counterexample.** It is a program
of that sound-but-incomplete kind, for a simpler vehicle than ours, with one unproven step. Section 3 goes through it.

## 1. What "lossless" means here, and why the definition is fair

`lean/LcvxObstruction/LcvxObstruction/Abstract.lean` defines a convex program with data θ = (r₀, v₀) as one convex
set C in (data, variables) space. It is lossless for the set F of landable initial states when, for every θ,

    the program is feasible at θ   ⟺   θ ∈ F.

Both directions matter. "⟹" is soundness. "⟸" is completeness. Theorem A is then six lines: F is the projection of
a convex set, so F is convex. If F is not convex, no such program exists.

I checked that this is not a straw man: classical 3-DoF LCvx satisfies it. There the thrust direction can switch
instantly, so the set of achievable impulses is convex (Lyapunov/Aumann), F is convex, and the relaxed program is
feasible exactly on F. The 5-DoF and 6-DoF sets fail the same test because the body cannot switch direction instantly.

## 3. The quoted result, taken apart

The construction: lock the engine to the body axis so the thrust direction *is* the attitude; impose the start
attitude, an upright landing, a turn-rate limit and a torque limit as convex constraints on the thrust vector; keep
the usual LCvx thrust relaxation; solve once.

| its claim | assessment |
|---|---|
| "Start attitude, upright landing, turn-rate limits and torque limits become convex constraints on the thrust vector." | True, as a **restriction**: the limits it imposes are stricter than the real ones (it says so). So it is sound for those limits and incomplete. This is allowed by Theorem A |
| "...together with the lossless thrust relaxation." | The relaxation ‖T‖ ≤ Γ is lossless only by the 3-DoF argument, which needs the thrust direction to be free. With rate limits on T that argument is gone. It reports the relaxation tight in 5 of 5 cases "with no proof behind it". When it is not tight the plan asks for less than minimum thrust and is not a trajectory at all |
| "A gimballed engine pushes the vehicle sideways when it steers, and that coupling is what makes true 6-DoF non-convex." | **Wrong on both counts.** The model *without* that coupling (thrust locked to a rate-limited body) is the one the Lean theorem proves nonconvex. And the coupling can be removed exactly: the centre of percussion does not feel the gimbal's sideways force |
| "For a gimballed-engine lander it gives a reference trajectory whose error has not been measured." | Measured here. A plan for a thrust-along-body point is followed by the centre of percussion, 1.35 m above the CG, not by the CG. On our cases the CG is 0.22 m (median) to 0.39 m off the planned path in mid-flight, and an initial body rate the plan did not account for moves the landing point by 0.41 m (median) to 0.88 m |
| "Lands within a micrometre when flown through the full nonlinear rigid-body equations." | An open-loop replay in the planning model with independent torque. It shows the plan is consistent with that model, not that the method is exact |

On our vehicle and our 70 cases, at the final time the other planners fly (first plans only):

| | in-air (40) | pad hop (30) |
|---|---|---|
| relaxation-based program feasible | 28 | 0 |
| relaxation tight where feasible | 28 of 28 | none feasible |
| extra flight time it needs where infeasible, median / max | 0.33 / 1.78 s | 0.80 / 1.47 s |
| planner F feasible | 40 | 29 |

So on first plans its relaxation was tight whenever it was feasible, which matches the "5 of 5". Two things do not
carry over. It is feasible far less often, because one bound on ‖Ṫ‖ and ‖T̈‖ has to cover direction changes and
throttle changes together, which rules out the fast throttle switch a fuel-efficient descent needs. And in closed
loop, where plans start from disturbed states, the same construction (candidate C in `solver/RESULTS.md`) produced at
least one non-tight replan in 34 of 40 in-air runs, down to ‖T‖/Γ = 0.80.

## 4. Mistakes found in this repository

None of them rescues LCvx. They are listed by how much they matter.

1. **A false practical conclusion.** `solver/RESULTS-SCVX.md` §4 said "every practical method must iterate on the
   attitude"; `solver/README.md` said any single-SOCP method "is either infeasible for the vehicle or loose
   somewhere" and used that to justify planner B's outer loop; `solver/CLAIMS.md` row 2 gave the theorem as "why B
   needs an outer loop at all". The theorem excludes sound-and-complete, not sound. `math/redteam-reform.md` §3.3
   did note a "sound inner test", but only the trivial one (the body never rotates), and called the resulting
   sandwich "the best a single convex program can do". Planner F is a single SOCP whose plans are all flyable and
   cost 0.1 % more fuel than the 6-DoF optimum at the operating point. Those sentences are corrected in place.
2. **Flatness was proved and then not used for planning.** FLAT is machine-checked, but `solver/CLAIMS.md` row 11
   lists it as "tracking controller only". Planning in CG coordinates is what makes the dynamics bilinear in attitude
   and thrust, and that is the only reason planners B and S need to linearise and iterate.
3. **Planners B and S plan with the wrong mass-property model.** They freeze J_t and L at their initial values while
   the mass drops, so their centre-of-percussion offset J_t/(mL) grows 6 % over a descent. The plant table keeps it
   within 1 %. Their certificates replay each plan in their own model (error below 1 mm) and never against the
   plant. Replayed open loop against the plant table, B and S plans miss by 0.43 and 0.45 m (median of 8 scenarios);
   planner F plans, which hold the offset constant, miss by 0.03 m. The closed loop hides this, but the tracker pays
   for it.
4. **The closed-loop comparisons gave every planner zero computation time.** Plans were applied at the instant the
   state was sampled. With each plan applied only after its measured solver time, planner B drops from 40/40 to
   36/40 in-air and from 29/30 to 28/30 on hops, and SCvx's median lateral error nearly doubles
   (RESULTS-FLAT.md §4). Solver time is part of landing accuracy and was not counted.
5. **Stale status.** `solver/CLAIMS.md` row 11 said FLAT was "not formalized" although `TVC.cop_identity` exists.
   Fixed.

## 5. Two follow-up questions

**"Impossible for every landing problem" does not rule out a usable subclass. Is there one?** Yes, of two kinds.

- *Restricting the vehicle.* LCvx is exact when the thrust vector can be steered without rotating the body, so that
  the attitude never has to move: the needed pointing cone fits inside the gimbal range of a body held still (X5 in
  `SYNTHESIS.md`). That needs a gimbal, or a cluster of engines, that steers thrust without producing the steering
  torque. On our vehicle the gimbal *is* the steering torque, so this class does not contain it. Removing the minimum
  throttle does not create a class either: with ρ₁ = 0 the vehicle can coast while it rotates, and the landable set is
  still nonconvex in a proved parameter regime (P0-F).
- *Restricting what the program promises.* A single convex program can be sound for the unrestricted vehicle if it
  gives up completeness. Planner F is that program for our gimballed vehicle. What it gives up is specific: it never
  uses tilt to throw thrust away (`math/10-landing-proof.md` §9), which is the manoeuvre the nonconvexity lives in.

**A roll-based proof says two roll directions can both be optimal. What if we ignore roll and do 5-DoF?** A proof of
that kind (two fuel-optimal trajectories that turn opposite ways about the roll axis, whose blends cannot be flown)
needs roll in the landing condition and a roll torque that costs no fuel. Dropping roll removes that example, and such
a proof says nothing about a single gimballed engine without roll torque. The proof in this repository is not of that
kind. It is 5-DoF from the start: three translations plus pitch and yaw of the thrust axis, no roll state
(`no_lossless_relaxation_constrained_5dof`). Its two equally good trajectories differ in the direction they *tilt*.
With a minimum throttle, shedding vertical impulse requires tilting, and tilting at the limit commits to one
direction; tilt-left and tilt-right are both flyable and their average is not. The hop-ring reproduction in section 2
was run with the roll rate held at zero. So the picture "two similar paths, both optimal" is right, but going to
5-DoF does not remove the pair. Everything in `solver/`, planner F included, already plans in 5-DoF with roll held by
the RCS.
